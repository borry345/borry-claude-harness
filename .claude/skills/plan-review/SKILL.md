# 기획 문서 독립 검토 절차

`ORCHESTRATION.md` "기획 문서 독립 검토"의 실행판이다. 원칙(왜·시점·트리거·검토자·상한)은 그쪽에
있고, 여기에는 **어떻게**만 둔다. 근거가 된 실측은 뱀서라이크 프로젝트 `RUN_LOG.md` 2026-10-16
항목과 하네스 `RUN_LOG.md` 2026-10-20 항목이다.

## 0. 트리거 확인 — 하나라도 해당하면 진행, 아니면 여기서 끝

- [ ] 기능 10개 이상 **또는** 수용 기준 100개 이상
- [ ] SPEC 개정이 2회 이상이었다
- [ ] **SPEC 마지막 개정 뒤에 확정된 결정이 있다** (규모 무관 — 그 결정이 문서에 없을 가능성이 가장 높다)

TECH_SPEC이 있으면 SPEC 직후 1회, TECH_SPEC 직후 1회로 **두 번** 돈다. 두 번째는 ③·④ 축이 중심이다.

## 1. 검토자 디스패치 프롬프트 골격

검토자는 작성자(spec-writer·tech-spec-writer)가 아닌 `general-purpose`(opus)다. 아래 블록을 **전부**
넣는다.

```
당신은 기획 문서 독립 검토자다. <프로젝트 루트>의 PRD.md, SPEC(<N>회차 — `SPEC.md` 또는 `spec/` 폴더 전체),
TECH_SPEC(<M>회차 — `TECH_SPEC.md` 또는 `tech/` 폴더 전체)을 읽고 PM에게 보고만 한다. 어떤 파일도 생성·수정하지 않는다.
DECISIONS.md의 <번호> 항목(없으면 RUN_LOG.md의 <날짜> 항목)은 SPEC 개정 뒤 확정된 결정이다 — SPEC·TECH와 충돌하면 결정 기록이 맞다.
```

- **① PRD → SPEC 커버리지**: PRD의 성공 기준·비목표·기능·미확정 항목 **각각의 행방을 표로**.
  내려오지 않은 것, 약해진 것(예: "비교해 설명할 수 있어야" → "측정만"), 비목표가 범위로 들어온
  것. **"답도 없이 목록에서 사라진 항목"이 핵심 대상**이다.
- **② SPEC 내부 일관성**: 같은 수치가 절마다 같은가(핵심 수치를 프롬프트에 나열해 준다) / 서로
  모순되는 수용 기준 / tester가 pass/fail을 낼 수 없게 쓰인 기준(주관적 표현, 측정 방법·기준값
  없음) / RUN_LOG의 확정 결정이 본문에 있는가 / 미확정 사항 절과 본문 참조의 정합.
- **③ SPEC → TECH_SPEC 정합**: 기능별 기술 수용 기준 존재 / TECH의 [기본값]이 SPEC 본문·기준과
  충돌하는가 / 데이터 스키마가 SPEC이 요구하는 필드를 전부 담는가 / 공유 규칙 표에 소유자 없는
  공유 규칙 / 소유권 맵에서 소유자 없음·이중 소유·미배정 기능.
- **④ 세 문서가 모두 놓친 것**: 도메인·런타임·배포 관점에서 어느 문서에도 규정이 없는 상황.
  **예시를 몇 개 주되 "이것만 보지 말고 스스로 더 찾으라"고 쓴다** — 예시만 보면 거기서 멈춘다.

```
보고 형식: [수정 필요 / 확인 권장 / 정보] 문서:절 — 무엇이 문제인가 — 제안 (한 줄씩)
  수정 필요 = 구현이 갈라지거나 PRD 목표가 빠지는 것 / 확인 권장 = 해석이 둘 이상 / 정보 = 사소
마지막에 심각도별 집계와, "수정 필요"를 소유 문서별(SPEC.md / TECH_SPEC.md)로 묶은 개정 지시 목록.
문제가 없는 축도 "이상 없음"으로 한 줄 남겨라. 근거 없는 추측은 쓰지 말고 확신이 없으면 "확인 권장"으로 낮춰라.
```

## 2. 검토 뒤 PM이 하는 일

1. **`git status`로 작업트리가 바뀌지 않았음을 확인**한다 — "수정 금지"는 프롬프트 지시일 뿐이다.
2. **선별**: 사용자 결정이 필요한 것(규칙 변경, 이미 확정된 결정의 번복)은 **한 번에 하나씩**
   추천안과 함께 묻는다. 나머지는 PM 기본값으로 정하고 `RUN_LOG.md`에 근거를 남긴다. 검토자의
   "확인 권장"도 전부 PM이 판정한다(수용 / 기본값 / 다음으로).
3. **소유 에이전트에게 개정 디스패치** — SPEC → spec-writer 먼저, 그다음 TECH_SPEC →
   tech-spec-writer. **순서 이유: TECH가 SPEC을 읽는다.** 개정 지시에는 항목 번호를 붙이고, 보고에
   **항목별 반영 위치 표**와 수용 기준 증감을 요구한다. 기존 ID·이름은 보존하라고 못 박는다.
4. **PM 드리프트 대조**는 그대로 한다(기능 ID·이름 보존). 이 검토가 그것을 대신하지 않는다 —
   둘은 다른 검사다.
5. 개정 중 에이전트가 새 공백을 보고하면(예: "작은 공백 5건") PM 기본값으로 **같은 턴에** 닫는다.
   소유 에이전트는 `SendMessage`로 이어서 호출하면 컨텍스트가 더운 상태라 싸다.

## 3. 2차 검토 프롬프트 골격 (범위를 좁힌다)

1차와 같은 조건의 **새** 독립 에이전트에게:

```
1차 "수정 필요" N건 각각에 대해 [해소 / 부분 해소 / 미해소] 문서:절 — 근거 한 줄.
보고를 믿지 말고 문서에서 직접 확인하라.
```

- 개정에서 추가·수정된 기준 전부와 TECH_SPEC의 정합(개정 표시를 기준으로 범위를 준다).
- TECH의 새 [기본값]이 SPEC과 충돌하는가.
- **개정이 새로 만든 모순** — 옛 수치·옛 이름·제거된 미확정 항목 ID 참조 같은 잔존 표현은
  grep으로 꼭 잡게 한다(실제로 "배속 4x", "측정 항목 5개", 사라진 Q 번호 참조가 남아 있었다).

## 4. 종료와 상한

- "수정 필요" 0건이면 종료. 남은 소폭 수정은 소유 에이전트를 `SendMessage`로 재개해 닫는다.
- 1라운드 = 1차 검토 → 개정 → 2차 검토. **2라운드를 넘기면 멈추고 사용자에게 보고한다.**
- 결과(건수, 가장 무거운 발견, 사용자 결정, PM 기본값)를 `RUN_LOG.md`에 남긴다. 특히 **PM 자신의
  절차 공백**(예: SPEC 개정 뒤 확정된 결정을 반영하지 않은 채 TECH를 디스패치)은 반드시 적는다.

## 5. 비용 기준 (실측, 운행마다 아래에 추가)

| 운행 | 1차 검토 | 2차 검토 | 개정 | 비고 |
|---|---|---|---|---|
| 2026-10-16 뱀서라이크(기능 19·수용 기준 274→328) | 236K 토큰·8분 → 수정 필요 22 / 확인 권장 30 / 정보 14 | 266K 토큰·6분 → 22건 전부 해소 확인 + 신규 5 | SPEC 4·5회차, TECH 2·3회차. `Edit` 없던 정의라 전체 재작성 2~3배 | 2라운드로 종료 |

**가장 무거웠던 발견**: PRD가 명시한 측정 항목이 SPEC에서 사라진 것, SPEC 마지막 개정 뒤 확정된
결정 4건이 SPEC에 없는 채 TECH의 입력이 된 것, 디스폰된 객체가 겹침 집합에 남아 계속 피해를 주는
설계 버그. **PM의 ID·이름 드리프트 대조는 이 셋 중 아무것도 잡지 못했다.**
