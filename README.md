# borry-claude-harness

Claude Code 위에서 **PM 세션(사용자와 대화하는 세션)이 전문 서브에이전트들을 조율해 프로젝트를
진행**하게 하는 하네스다. 코드가 아니라 문서·에이전트 정의·권한 설정·스킬로 이루어져 있고, 어떤
프로젝트 루트에 설치해도 그대로 동작한다. 프로젝트 콘텐츠(코드, 프로젝트별 스펙)는 담지 않는다.

- 가장 먼저 할 일 → [1. Quick start — 설치](#1-quick-start--설치)
- 설치 뒤 어떻게 굴러가는지 → [2. 사용 가이드 — 워크플로우](#2-사용-가이드--워크플로우)
- 규칙의 원본은 `ORCHESTRATION.md`·`CODING_GUIDE.md`이고, `CLAUDE.md`가 그 지도다. 이 README는
  진입용 요약이며 규칙을 새로 정하지 않는다 — 둘이 다르면 원본 문서가 맞다.

## 1. Quick start — 설치

**전제**: Claude Code, git, POSIX 셸(`sh` — Windows는 Git Bash). 설치 대상은 **프로젝트 루트이며
git 저장소**여야 한다(승인 게이트와 체크포인트 커밋이 git 위에서 동작한다).

### 1-1. 하네스를 받는다 (프로젝트 바깥에)

```sh
git clone https://github.com/borry345/borry-claude-harness.git
```

하네스 클론은 프로젝트 폴더 **안에 두지 않는다**. 형제 폴더나 별도 위치에 둔다.

### 1-2. 프로젝트 루트에 설치한다

```sh
sh <하네스 폴더>/scripts/install-into-project.sh <프로젝트 루트>
# 이미 있는 파일을 덮어쓰려면: ... <프로젝트 루트> --force
```

스크립트는 다음을 프로젝트 루트에 **복사**한다(이미 있는 파일은 `--force` 없이는 건너뛴다):

| 복사되는 것 | 역할 |
|---|---|
| `CLAUDE.md` | Claude Code가 자동 로드하는 지도 — 반드시 프로젝트 **최상위** 루트에 있어야 한다 |
| `HANDOFF.md`, `ORCHESTRATION.md`, `CODING_GUIDE.md`, `DESIGN_NOTES.md` | PM이 세션 시작 때 읽는 규칙 문서 |
| `.claude/agents/*.md` | 전문 에이전트 6종 정의 (spec-writer, tech-spec-writer, team-lead, tester, doc-writer, agent-builder) |
| `.claude/skills/*/SKILL.md` | 반복 절차 6종 (필요할 때만 로드) |
| `.claude/settings.json` | 권한 설정 — `git commit/tag/push/reset`, `npm install` 등 **승인 게이트**, `.env` 읽기·강제 푸시 **차단** |
| `scripts/checkpoint-commit.sh` | team-lead가 통합 직후 남기는 체크포인트 커밋 스크립트 |

복사되지 **않는** 것: 하네스 자체의 이력(`RUN_LOG.md`, `CHANGELOG.md`, `reviews/`, `.git`).
`.claude/settings.json`은 기존 파일이 있으면 `--force`로도 덮어쓰기 전에 직접 병합 여부를 판단한다
(스크립트가 차이를 경고한다).

### 1-3. 설치를 확인한다

프로젝트 루트에 아래가 있으면 된다.

```text
<프로젝트 루트>/
├── CLAUDE.md
├── HANDOFF.md  ORCHESTRATION.md  CODING_GUIDE.md  DESIGN_NOTES.md
├── .claude/
│   ├── agents/      (6개 .md)
│   ├── skills/      (6개 폴더)
│   └── settings.json
└── scripts/checkpoint-commit.sh
```

### 1-4. 프로젝트 루트에서 Claude Code를 열고 workspace trust를 수락한다

- `CLAUDE.md`가 자동 로드되면 PM은 `HANDOFF.md` → `ORCHESTRATION.md` → `CODING_GUIDE.md` 순으로 읽고 시작한다.
- `permissions.deny`·`ask`(차단·승인 게이트)는 즉시 적용되지만, **`permissions.allow`(체크포인트 커밋
  자동 실행)와 `env`는 폴더 trust를 수락한 뒤에만 적용된다.** 수락 전에는 체크포인트도 승인 프롬프트가 뜬다.
- PM 세션 모델은 fable(가능하면), 아니면 opus로 연다. 하위 에이전트 모델은 PM이 호출할 때 `model` 인자로 넘긴다.

### 1-5. 프로젝트 전용 문서를 만든다

설치본에는 프로젝트 문서가 없다. PM이 착수 때 프로젝트 루트에 **`RUN_LOG.md`**(결정·이유·실패 이력,
append-only)를 만든다. `SPEC.md`(필요하면 `PRD.md`, `TECH_SPEC.md`)는 아래 워크플로우에서 에이전트가 만든다.
`.gitignore`에는 최소 `.env`·`.env.*`·`.scratch/`를 넣는다.

### 흔한 실수

- **하네스 폴더를 옆에 두고 프로젝트에서 작업하기** — `CLAUDE.md` 자동 로드, 승인 게이트, 체크포인트가
  전부 꺼진다. 반드시 프로젝트 루트에 설치한다.
- **하네스 폴더 안에 프로젝트를 만들기** — 다음 프로젝트에 재사용할 때 다시 정리해야 한다.
- **하네스 업데이트**: 하네스 클론에서 `git pull` 뒤 같은 스크립트를 `--force`로 다시 실행한다.
  프로젝트 쪽 `settings.json`을 손봤다면 덮어쓰기 전에 병합한다.

## 2. 사용 가이드 — 워크플로우

### 2-1. 큰 틀 — 사용자 입장에서 본 흐름

```text
⓪ 설치 ─▶ ① 자연어 명세 ─▶ ② 명세화 ─▶ ③ 기획 문서 독립 검토 ─▶ ④ 구현 ─▶ ⑤ 통합 테스트 ─▶ ⑥ 마감 ─▶ (필요시) ⑦ 릴리스 교차검증
                                                                 ▲              │
                                                                 └── 실패 재작업 ┘
```

| 단계 | 사용자가 하는 것 | PM과 에이전트가 하는 것 | 나오는 것 |
|---|---|---|---|
| **⓪ 설치** | 1장대로 프로젝트 루트에 설치하고, 그 루트에서 Claude Code를 연다 | PM이 `HANDOFF.md`부터 읽고 프로젝트 전용 `RUN_LOG.md`를 만든다 | 설치본, `RUN_LOG.md` |
| **① 자연어 명세** | 만들고 싶은 것을 말로 설명한다. 완벽할 필요 없다. README 같은 문서를 직접 쓸지 이때 정한다 | PM이 되묻고, 규모가 크거나 목표가 흐리면 PRD 단계를 제안한다 | (대화) |
| **② 명세화** | PM이 하나씩 묻는 미확정 사항에 답한다. 답하지 않은 항목은 확정되지 않는다 | spec-writer가 `SPEC.md`(필요하면 `PRD.md` 먼저), 기존 코드·외부 프로토콜이 핵심이면 tech-spec-writer가 `TECH_SPEC.md`를 쓴다. 확정된 결정은 바로 문서에 반영한다 | `SPEC.md`, `TECH_SPEC.md` |
| **③ 기획 문서 독립 검토** (규모가 크면) | 검토 결과 중 결정이 필요한 것만 답한다. 프로젝트가 크면 PM의 제안에 따라 구현을 **새 세션**에서 이어갈지 정한다 | 맥락 없는 독립 에이전트가 PRD·SPEC·TECH_SPEC을 서로 대조하고, PM이 선별해 소유 에이전트에게 개정시킨다. 2라운드가 상한 | 확정된 명세 |
| **④ 구현** | 승인 프롬프트(`git commit`, `npm install` 등)에 응답한다 | PM이 기능별 구현자를 디스패치하고 team-lead가 통합·체크포인트 커밋 | 동작하는 코드 |
| **⑤ 통합 테스트** | 같은 기능이 3회 연속 실패하면 어떻게 할지 정한다 | tester가 수용 기준별로 검증하고, 실패는 ④로 돌려 재작업. 위험한 기능은 독립 검증 모드를 한 번 더 | 기능별 pass/fail |
| **⑥ 마감** | 자동 검증이 못 닿는 항목(브라우저, 외부 서비스 설정)을 직접 확인하고, 커밋·태그·푸시를 승인한다 | doc-writer가 사용자용 문서를 쓰고, PM이 종료 체크리스트(작업트리·시크릿·스크래치 정리·검증 한계 명시)를 거쳐 보고한다 | 사용자용 문서, 커밋 |
| **⑦ 릴리스 교차검증** (필요시, 하네스 업데이트) | 검토용으로 **다른 PM 세션**을 연다 | 이번 운행에서 얻은 하네스 레벨 교훈을 하네스 저장소에 반영하고(`[Unreleased]`), 그 변경을 만들지 않은 다른 PM 세션이 공식 문서 기준으로 검증한다(`reviews/`). 시험을 거친 뒤 태그하고, 프로젝트의 설치본을 `--force`로 동기화한다 | 하네스 새 버전, 동기화된 설치본 |

- ②와 ③은 작은 프로젝트면 한 번에 지나간다. ③은 기능 10개 이상, 수용 기준 100개 이상, 스펙 개정 2회 이상,
  또는 마지막 개정 뒤 확정된 결정이 있을 때만 돈다.
- ④와 ⑤는 기능 묶음마다 반복된다. 큰 프로젝트는 PM이 ③ 끝에서 세션을 기획 / 구현 / 마감 셋으로 나누자고 제안한다.
- ⑦은 하네스를 손댄 운행에만 있다. 프로젝트 쪽 교훈은 프로젝트 `RUN_LOG.md`에, 하네스 쪽 교훈은 하네스 `RUN_LOG.md`에 적는다.
- "검토"와 "검증"이 세 번 나온다 — ③ 기획 문서 독립 검토(독립 에이전트), ⑤ 통합 테스트(tester), ⑦ 릴리스 교차검증(다른 PM 세션).
  대상과 주체가 전부 다르고 서로 대신하지 못한다.

각 단계에서 PM이 실제로 무엇을 하는지는 아래 상세 흐름에 있다.

### 2-2. 역할

| 자리 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **PM** (사용자 대화 세션) | 에이전트 선택·호출, 사용자 결정 수집, 인터페이스 계약 작성, `RUN_LOG.md` 기록, 완료 보고 | 소스 코드 직접 작성, 빌드·테스트 직접 실행, 큰 파일 통째로 읽기 |
| spec-writer | 자연어 요구 → `SPEC.md` (기능별 요구사항·수용 기준·미확정 사항). 규모가 크면 먼저 PRD 모드로 `PRD.md` | 모호한 요구를 추측해 확정 |
| tech-spec-writer | 기존 코드·외부 문서를 읽고 `TECH_SPEC.md` (설계, 소유권 맵·계약 초안) | 기능 범위 결정, 코드 수정·실행 |
| 구현 에이전트 | 기능별로 자기 스크래치 디렉터리 안에서 구현 | 공유 경로에 직접 쓰기 |
| team-lead | 구현물 조립·통합, 체크포인트 커밋, 병합 품질 체크리스트, **PM이 전달한** tester 판정으로 SPEC 체크 | 스스로 완료 판정, tester 호출, 스펙 밖 기능 추가 |
| tester | 수용 기준별 테스트 작성·실행, pass/fail과 원인 보고 (Tier 1 기본, 독립 검증 모드 선택) | 로직 버그 수정 |
| doc-writer | 정리된 내용을 사용자용 문서로 포맷팅 | 스스로 조사 |
| agent-builder | PM 스펙으로 새 에이전트 정의 파일 작성 | 역할 스스로 결정 |

**모든 호출은 PM에서 나간다.** 에이전트가 에이전트를 부르는 구조는 전제하지 않는다(중첩 호출의
포그라운드 대기가 보장되지 않아서). 에이전트가 다른 에이전트의 결과가 필요하면 PM이 연달아 호출해 전달한다.

### 2-3. 상세 흐름 — PM 기준

```text
사용자 설명
  │
  ├─(규모 크거나 목표가 불명확하면) spec-writer [PRD 모드] ──▶ PRD.md
  ▼
① spec-writer ──▶ SPEC.md            PM이 미확정 사항을 사용자에게 "한 번에 하나씩" 확인
  │
  ├─(기존 코드·외부 프로토콜 이해가 핵심이면) tech-spec-writer ──▶ TECH_SPEC.md
  ▼
② 기획 문서 독립 검토 (트리거 충족 시, plan-review 스킬)   ·   세션 분리 판단
  ▼
③ 구현 디스패치 (dispatch-implementer 스킬)   기능별 에이전트, 각자 .scratch/<이름>/ 안에서
  ▼
④ team-lead 통합 ──▶ checkpoint-commit.sh ──▶ "검증 준비됨" + 기능 그룹 보고
  ▼
⑤ tester (PM이 그룹별로 호출) ──▶ 판정 ──▶ PM이 team-lead에 전달 ──▶ SPEC 체크 / 재작업
  ▼                                        (같은 기능 3회 연속 실패 = 3-strikes, 사용자에게 보고)
⑥ doc-writer ──▶ 사용자용 README/사용법
  ▼
⑦ PM 종료 체크리스트 ──▶ pre-push-check 스킬 ──▶ 의미있는 커밋·태그·푸시는 사용자 승인 후
```

단계별 요점:

1. **스펙** — `SPEC.md`는 spec-writer만 쓴다(파일 소유권: 한 파일 = 한 소유자). 미확정 사항은 PM이
   사용자에게 하나씩 묻고, **무응답은 동의가 아니다.** 확정된 결정은 같은 턴에 `RUN_LOG.md`에 적고
   소유 에이전트에게 문서 개정을 지시한다. 사용자가 PM 추천과 다르게 정하면 "PM 추천 → 사용자 변경"으로 남긴다.
2. **독립 검토** — 기능 10개 이상, 수용 기준 100개 이상, SPEC 개정 2회 이상, 또는 마지막 개정 뒤
   확정된 결정이 있으면 맥락 없는 독립 에이전트가 PRD·SPEC·TECH_SPEC을 교차 점검한다. 2라운드가 상한.
3. **구현 디스패치** — PM이 각 구현자에게 배타적 경로, 스크래치 디렉터리, 인터페이스 계약(시그니처·필드명·
   공통 규칙의 단일 소유자), `SPEC.md`와 `CODING_GUIDE.md`, 기준선(baseline-handoff 스킬)을 함께 준다.
   구현자는 파일 단위 변경 요약으로 보고한다.
4. **통합** — team-lead가 소유권 맵대로 스크래치에서 최종 경로로 조립하고 체크포인트 커밋을 남긴다.
   동작이 다른 중복 로직은 고르지 않고 PM에게 올린다.
5. **검증** — tester 호출 단위는 기능 6개 이하의 그룹. PM이 매 호출에 `model`과 tier를 넘기고 `RUN_LOG.md`에
   한 줄 남긴다. 구현자의 "됐다"는 검증이 아니다. 위험도가 높으면 독립 검증 모드(team-lead 맥락 차단)를 켠다.
6. **마감** — `git status`와 시크릿 스캔, `.scratch/`·빌드 사본이 디스크에 남지 않았는지, 검증이 닿지 않은
   영역(브라우저·외부 서비스)의 수동 체크리스트, "완료"의 의미를 보고에 명시한다.

### 2-4. 매 세션 시작 때 확인할 것

- Agent 도구의 `subagent_type` 목록에 커스텀 이름(`spec-writer`, `team-lead` …)이 **보이면 그대로 쓴다.**
  안 보이면 `general-purpose` + "`.claude/agents/<이름>.md` 정의를 따르라"로 우회한다 — 이때 정의 파일의
  `model:`·`tools:`는 적용되지 않으므로 모델은 호출 인자로, 도구 제한은 소프트 제약으로 본다.
- Agent 도구에 `run_in_background` 파라미터가 있는지 본다. 없으면 포그라운드를 요청할 수 없는 세션이다.
- 현재 세션 모델이 PM 기준(fable/opus)에 맞는지 본다. 아니면 사용자에게 알린다.

### 2-5. 승인 게이트와 커밋 이원화

| 동작 | 설정 | 의미 |
|---|---|---|
| `git commit`, `git tag`, `git push`, `git reset`, `git rm`, `git clean`, `rm -rf`, `npm install` 등 | `ask` | 매번 사용자 승인. "PM도 임의로 커밋하지 않는다"의 기술적 구현 |
| `git push --force`, `.env`·`env.js` 읽기 | `deny` | 차단 |
| `scripts/checkpoint-commit.sh` | `allow` | 승인 없이 실행(trust 수락 후). 통합 직후 롤백 지점 전용 — 의미있는 커밋은 여기 쓰지 않는다 |
