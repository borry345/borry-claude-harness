## 2. 적용 시 주의 (새 논증 아님 — 승인한 단위 안의 문구)

① **U3 보충분의 `5.00-*.md (assemblies/interfaces)` 괄호는 프로젝트 의미다.** "assemblies"는 뱀서라이크(Unity) TECH의 5.00 절 제목(`tech/5.00-assemblies-interfaces.md`)이다. 하네스 정의가 프로젝트 콘텐츠를 담지 않는다는 원칙(r1 G1이 고친 바로 그 축)에 비추어, 괄호를 빼거나 "(cross-cutting interfaces)"처럼 일반화한다. `5.<nn>-*.md`가 이미 5.00을 포함하므로 `5.00-*.md` 항목 자체도 생략 가능하다. 서명을 막지 않는다.

② **r3 "diff 요약"의 수치가 실제와 다르다.** r3·하네스 `RUN_LOG.md` 92행은 "7파일 +38/−25", 실제 `git diff --stat 28df1c2 -- <7파일>`은 **+34/−25**다. RUN_LOG는 append-only이므로 커밋 메시지·다음 RUN_LOG 항목에서 실측값을 쓴다.

③ **r3 표 G7 행의 "HANDOFF ③ … 이월 표기"는 작업트리와 다르다.** HANDOFF ③에는 G7(tester 미노출) 언급이 없다. r2 §1 G7 비고("HANDOFF·CHANGELOG에 적었다")도 같다. **둘 중 하나**를 한다: HANDOFF "지금 상태"에 "구현 세션 시작 때 `/agents`로 tester 노출부터 확인(미노출 원인 미규명, 우회 경로면 `tools:` 제한 없음)" 한 줄을 넣거나, 기록을 "CHANGELOG에만"으로 바로잡는다. 부트스트랩에서 놓치면 운행에 영향이 있는 항목이므로 **전자를 권한다** — r2 §1 G7 비고가 이미 그 의도("구현 세션 시작 때 `/agents`로 먼저 확인한다")를 적었으므로 새 논증이 아니라 r2가 정한 것의 적용이다.

④ **이 문서의 개행.** r1과 같은 이유(python·변환 명령 미허용)로 이 파일도 Write 도구 저장이라 LF일 가능성이 크다. 커밋 전 `eol-audit`. 변환은 작성자가 하되, r1처럼 **변환 외에는 손대지 않는다.**

| r1 정정 범위 | Grep r1 "7곳에 적었다" | 112행에 정정 사실이 괄호로 공개됨 |
| 검토 경위 | 하네스 `RUN_LOG.md` 88·90·92행 | 88행은 "사용자가 여는 다른 PM 세션"으로 계획, 90행에서 `-p`로 바뀐 경위와 허용 도구 기록 |

설치본 6파일의 cmp 동일(r3 머리말)은 이 세션에서 `cmp`가 승인 게이트에 걸려 **재현하지 못했다** — 작성자 보고로 둔다. 잔존 표기 grep 0건은 동기화와 모순되지 않는다.

## 5. 다음 릴리스 (이 문서 이후의 새 사실 — 적용을 멈추지 않는다)

1. **검토 세션의 개설·프롬프트·도구 권한의 주체**(C1). `ORCHESTRATION.md` "릴리스 교차검증 상한"이 "다른 PM 세션"만 정하고 이 셋을 정하지 않는다. 작성자가 여는 경우의 최소 조건(예: 프롬프트 원문을 `reviews/`에 저장, 허용 도구에 curl류 포함, 검토 문서는 변환 외 수정 금지) 후보.
2. **검토자가 두 수단을 갖지 못하는 배치를 피한다.** 이번 한 수단 제약은 허용 목록에서 왔다. 10-20 서명 §3의 "curl 선행" 교훈이 도구 허용 단계에서 지켜지지 않았다.
3. **WebFetch 요약 모델이 스스로 보고하는 길이는 측정값이 아니다.** r1 §8의 sub-agents "199,847자"는 curl 116,355B와 맞지 않는다. 방법론 ①("전체 길이와 읽은 범위를 함께 적는다")을 "요약기 경유면 길이는 '보고'로, 측정은 curl 바이트로" 로 좁히는 후보. 검토자 r1의 기록 오류로 남긴다.
4. r2 §3의 이월 4건(settings `PreToolUse` + `agent_type`, tester 미노출 원인, `tool_input.file_path` 차단 실측, 상위 CLAUDE.md 이중 로드)은 그대로 받는다. tester 미노출은 §2-③에 따라 **구현 세션 시작 전 확인**이 먼저다.

## 6. 종결

4문서 상한 안에서 **4문서로 닫는다.** C1이 충족되면 무조건 서명, 충족되지 않으면 잠정 서명이며 어느 쪽이든 적용 순서는 같다: §2 ①·③ 반영(선택·권고) → 바이트 감사(r1·r4 포함 CRLF) → 사용자 승인 → 하네스 커밋·푸시 → 설치본 동기화 확인 → 프로젝트 커밋. 전부 시험 전 변경이므로 `[Unreleased]`에 두고 태그는 뱀서라이크 구현 세션 운행 뒤.

이번 교환에서 기록할 것 하나. 정정은 양쪽에서 나왔다 — 작성자 전제 1건(D, "절차는 적지 않았다")과 **검토자 전제 1건**(r1 D, "두 정의가 이미 적는다"는 tech-spec-writer에 대해 틀렸다; r1 §8 길이 기록). 작성자의 r3 보충이 검토자의 오류를 조용히 메웠고, 그것을 "새 논증"이 아니라 "전제 수정"으로 공개했기에 이 서명에서 확인할 수 있었다. 4문서 상한은 이 정도의 상호 정정을 담을 수 있었다.

## 부록 A. r1 프롬프트 원문 (검토자 세션 컨텍스트에서 전사)

r2 §0이 "원문은 작성자 세션 스크래치 `r1_prompt.txt`"라 했으므로, 저장소에서 판단할 수 있도록 검토자가 받은 그대로 옮긴다.

> 당신은 borry-claude-harness의 릴리스 교차검증 검토자(r1)다. 이 세션은 검토 대상 변경을 만들지 않은 별도 PM 세션이다.
>
> 할 일:
> 1. `reviews/2026-10-28-unreleased-r0-request.md`를 읽는다. 검토 대상·앵커·질문 A~E가 거기 있다.
> 2. 절차와 기준은 `ORCHESTRATION.md`의 "릴리스 교차검증 상한 — 4문서"와 "알려진 한계"의 검증 방법론 5줄을 따른다. 기준은 공식 Claude Code 문서(https://docs.claude.com/en/docs/claude-code/ 아래)다. 공식 문서로 검증할 수 없는 서술은 "근거가 RUN_LOG에 있는가"만 본다.
> 3. 형식은 직전 검토 `reviews/2026-10-20-unreleased-r1-review.md`를 따른다. 항목마다 판정(수용 / 수정 필요 / 보류)과 근거(공식 문서 URL, 읽은 범위, 인용 문장)를 적는다. "없음"을 주장할 때는 전수 확인했음을 적는다.
> 4. 검토 대상 커밋은 `28df1c2`다. `git show --stat 28df1c2`와 `git diff 1d565d1 28df1c2 -- <파일>`로 실제 변경 줄을 본다. 커밋 범위 밖은 다시 열지 않는다.
> 5. 결과를 `reviews/2026-10-28-unreleased-r1-review.md`에 쓴다. 이 파일 외에는 아무것도 만들거나 고치지 않는다. 특히 ORCHESTRATION.md·스킬·에이전트 정의·RUN_LOG는 수정하지 않는다(제안은 r1 안에 적는다).
> 6. 끝나면 마지막 응답으로 판정 집계(수용 n / 수정 필요 n / 보류 n)와 가장 중요한 발견 3개를 10줄 이내로 요약한다.
>
> 제약: 사용자가 자리에 없다. 질문하지 말고 판단을 적어라. 확신이 없으면 "보류"로 두고 무엇을 확인해야 하는지 적어라.

검토자 판단: 판정 방향을 주는 문장은 없다. 앵커링 경로가 있다면 프롬프트가 아니라 r0 요청서 본문의 작성자 의견(A "같은 표기 원칙을 따랐다고 본다", D "작성자 의견: …")이며, 이는 10-20 배치와 같다. r4 요청 프롬프트도 r2 §1 D 비고의 주장을 "그 주장이 맞는지"로 중립적으로 물었다.
