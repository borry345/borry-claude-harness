## 3. 결함 — 공식 기준으로 틀렸거나 좁은 것

### F1. `Write(...)` deny 규칙은 조회되지 않는 죽은 규칙이다

- **대상**: `1649641/.claude/settings.json`의 `Write(./LogDataManagement/functions/**)` 등 **5줄**.
- **공식 근거**: permissions — "Claude Code checks file permissions against `Edit(path)` and
  `Read(path)` rules only. If you write a path rule for `Write`, `NotebookEdit`, `Glob`, or the
  legacy `MultiEdit` tool instead, Claude Code accepts the rule but never consults it, and warns at
  startup... Use `Edit(docs/**)` in place of `Write(docs/**)`."
- **증거**: 해당 파일에 `Edit(...)`와 `Write(...)`가 같은 경로로 쌍을 이뤄 들어 있다.
- **영향**: **실제 차단 효과는 변하지 않는다**(쌍을 이룬 `Edit(...)`가 Write 도구까지 덮기 때문).
  영향은 ① 시작 시 무효 설정 경고 ② "Write도 막아뒀다"는 잘못된 안전 인식.
- **제안**: `Write(...)` 5줄 삭제. `Edit(...)`만 남긴다. `.ipynb`를 쓰게 되면 그때
  `NotebookEdit`은 Read deny로 덮이지 않으므로 별도 `Edit` 규칙이 필요하다.
- **교차검증**: 공식 permissions 페이지에서 "never consults it" 문단을 확인. 그리고 실제 세션
  시작 시 무효 설정 경고가 뜨는지(또는 `claude doctor`의 resolved settings) 확인.

### F2. `env.js`/`.env` 차단 범위가 실물 파일 분포보다 좁다 (실 구멍)

- **대상**: 하네스·사본 양쪽의 `Read(./env.js)`, `Read(./.env)`, `Read(./.env.*)`.
- **공식 근거**: permissions — 경로 규칙은 gitignore 문법이고 `./path`는 "Path relative to current
  directory"로 **그 위치 하나**를 가리킨다. 반면 "Bare filenames follow gitignore semantics and
  match at any depth, so `Read(.env)` and `Read(**/.env)` are equivalent."
- **증거**(이 머신 실측, `find` + `.gitignore` 대조): `env.js`가 `./env.js` 외에 `./dist/env.js`와
  `.scratch/` 아래 8곳에 실재한다(총 10개). 현재 규칙은 그중 **1개만** 덮는다.
- **영향**: 서브에이전트가 `dist/env.js`나 `.scratch/*/env.js`를 **읽을 수 있다**. 단 저장소
  유출은 아니다 — `env.js`, `dist/`, `.scratch/`가 `.gitignore`에 있고 `git ls-files`에 0건,
  작업트리도 깨끗하다.
- **제안**: `Read(**/.env)`, `Read(**/.env.*)`, `Read(**/env.js)`로 교체(공식 문서가 동등하다고
  명시한 베어 파일명 형태). 하네스 기본값에도 같이 적용.
- **교차검증**: `find . -name "env.js" -not -path "*/node_modules/*"`로 사본 개수 확인 →
  공식 permissions의 "Deny rule / Blocks / Does not block" 표에서 `Read(.env)` 행 확인.

### F3. deny의 한계 서술이 공식과 다르다 — 실제보다 약하게 적었다

- **대상**: `ORCHESTRATION.md` "알려진 한계"의 "`deny`는 **도구 단위**라 `Read(./env.js)`를 막아도
  `Bash(cat env.js)`는 다른 경로다".
- **공식 근거**: permissions — "Read and Edit deny rules apply to Claude's built-in file tools,
  **to file commands Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, `sed`, and
  `tee`**, and to the targets of Bash redirections such as `> file` and `< file`. They don't apply
  to a command that reads files without naming them, such as `grep -r pattern .`... or to arbitrary
  subprocesses that read or write files indirectly, like a Python or Node script."
- **영향**: 서술이 틀렸을 뿐 아니라 **결론의 방향이 바뀐다**. `Bash(cat ...)`는 이미 막힌다. 남는
  빈틈은 (a) 파일명을 적지 않는 명령 (b) 파일을 직접 여는 하위 프로세스다. 또한 공식은 모든
  프로세스를 막는 수단으로 훅이 아니라 **sandbox**를 지목한다 — "For OS-level enforcement that
  blocks all processes from accessing a path, enable the sandbox."
- **제안**: 해당 문단을 위 두 빈틈으로 정정하고, `DESIGN_NOTES.md` B1(훅)의 대안으로 sandbox를
  나란히 적는다. B1을 "유일한 완전 강제"로 서술한 부분도 같이 정정한다.
- **교차검증**: 공식 permissions의 Note 문단(Read/Edit 규칙이 Bash 파일 명령에도 적용) 확인.

### F4. `Bash(git push --force:*)`는 플래그가 뒤에 오면 비껴간다

- **공식 근거**: permissions — "The `:*` suffix is an equivalent way to write a trailing wildcard,
  so `Bash(ls:*)` matches the same commands as `Bash(ls *)`"; "A `*` at the end, with a space
  before it, also matches the bare command"; "The space before a trailing `*` is part of the rule".
  Bash 규칙은 접두 매칭이며 `Bash(git push *)`조차 `git -C . push`를 잡지 못한다.
- **판정 결과**:
  - `git push --force`, `git push --force origin main` → **막힌다**.
  - `git push --force-with-lease` → **막히지 않는다**(`--force` 뒤 공백이 규칙의 일부). 안전한
    변형을 하드 차단하지 않으므로 **의도에 부합**한다. 우연히 맞은 쪽.
  - `git push origin main --force` → **막히지 않는다**. 접두 매칭이라서다.
- **영향**: 강제 푸시의 흔한 작성 순서 하나가 deny를 통과한다. 다만 `ask`의 `Bash(git push:*)`가
  2차 그물이라 무승인 실행은 아니고 프롬프트가 뜬다.
- **제안**: 강제성이 필요하면 `Bash(git push *--force*)`를 추가한다(위치 무관 `*` 매칭). 단 이때
  `--force-with-lease`도 같이 막히므로, 그걸 허용할지 먼저 정해야 한다. **이 패턴은 아직 실측하지
  않았다** — §4 U4.
- **교차검증**: 공식의 wildcard 패턴 절 확인 후, 임시 저장소에서 각 형태를 실제로 입력해 프롬프트가
  뜨는지 관찰.

### F5. 같은 릴리스가 자기 근거를 어겼다 (구조 문제)

- **대상**: `CLAUDE.md` 신설 행 "절차를 `ORCHESTRATION.md`에 더 쌓지 말고 여기에 둔다 — 그 파일은
  매 세션 전량 로드된다" vs 같은 커밋의 `ORCHESTRATION.md` **+59줄**("실행 라운드에서 얻은 규칙"
  10항목 등).
- **증거**: `ORCHESTRATION.md` 426 → 475줄(실측). `CLAUDE.md`가 이 파일을 "항상 읽는다"로 지정.
- **공식 근거**: skills — 상세는 보조 파일로 내리고 필요할 때 로드하는 progressive disclosure가
  스킬의 설계 목적이다. 상시 로드 경로에 절차를 쌓는 것은 그 반대 방향이다.
- **영향**: 스킬을 도입했는데 상시 컨텍스트 비용은 오히려 늘었다. v0.2.2는 "스킬로 옮겼다"가
  아니라 "스킬을 시작했다"가 정확한 서술이다.
- **제안**: 10항목을 성격대로 이동 — 디스패치 문구는 `dispatch-implementer`, 결정성·기준선은
  `baseline-handoff`, 개행은 `eol-audit`. `ORCHESTRATION.md`에는 원칙 한 줄 + 스킬 포인터만 남긴다.
- **교차검증**: 10항목을 하나씩 읽고 "원칙(왜)인가 절차(어떻게)인가"로 분류. 절차 쪽이 다수면 이
  지적이 성립한다.

### F6. `allow` 규칙은 workspace trust 수락 후에만 적용된다

- **대상**: `.claude/settings.json`의 `allow` 3줄(체크포인트 커밋 자동 실행) — v0.2.2가 아니라
  v0.2.0부터 있던 것이지만, v0.2.2가 trust 함정을 문서화하면서 자기 `allow`에는 적지 않았다.
- **공식 근거**: settings — "`permissions.allow` rules, `permissions.additionalDirectories`,
  `extraKnownMarketplaces`, and most `env` values apply only after each teammate trusts the
  folder... `deny` and `ask` rules apply right away."
- **영향**: trust를 수락하지 않은 환경에서는 체크포인트 커밋이 **무승인 자동 실행되지 않고** 승인
  프롬프트가 뜬다. "체크포인트는 승인 없이 돌아간다"는 설계 전제가 조건부다.
- **제안**: `install-into-project.sh`의 사후 안내에 "이 폴더의 workspace trust를 수락해야 `allow`와
  프런트매터 훅이 적용된다"를 추가하고, `ORCHESTRATION.md`의 체크포인트 이원화 설명에 같은 조건을
  한 줄로 단다.
- **교차검증**: 공식 settings의 "The key waits for trust" 항목 확인.

## 5. 내가 확인하지 못한 것 / 불확실한 것

교차검증자가 **먼저 의심해야 할 칸**이다.

- **U1. v0.2.2의 `debugger` 예시 인용.** `CHANGELOG.md`는 "공식 문서의 `debugger` 예시도 `Edit`만
  주고 `Write`는 주지 않는다"고 적었다. 2026-10-16에 받은 sub-agents 페이지에서는 `debugger` CLI
  예시에 **`tools` 필드가 없다**(즉 전체 상속)고 읽혔다. 문서 버전 차이일 수 있고, 페이지 전체를
  읽은 것은 아니다(앞 100,000자만 확인). **결론 자체(문서 에이전트에 Edit 부여)는 다른 근거로
  충분히 서지만, 이 인용 한 줄은 재확인이 필요하다.**
- **U2. `Edit|Write` + `tool_input.file_path` 훅 패턴.** 공식 sub-agents 페이지의 `PreToolUse`
  예시는 **Bash matcher + `.tool_input.command`**이고, `Edit|Write` matcher는 `PostToolUse`
  (린터) 예시에만 나온다. B1이 전제하는 "`PreToolUse`에서 `file_path`를 검사해 차단"은 합리적
  유추이지만 **공식 예시로 확인된 형태는 아니다.** 도입 전 최소 1회 실측이 필요하다.
- **U3. 우회 경로(`general-purpose` + 정의 파일 따르기)에서 `tools:`가 무시되는지.** v0.2.1·v0.2.2
  모두 미측정으로 남겼고, 나도 측정하지 않았다. 네이티브 경로에서 강제되는 것만 확인됐다.
- **U4. F4의 제안 패턴(`Bash(git push *--force*)`)은 실측하지 않았다.** 공식의 와일드카드 서술에서
  추론한 것이다.
- **U5. 공식 문서는 2026-10-16 시점 스냅샷이다.** 필드 표와 도구 목록은 버전마다 바뀌어 왔다
  (이 하네스 자신이 중첩 호출 지원이 버전마다 달라진 사례를 기록했다). 날짜가 지나면 재확인한다.
- **U6. 비용·효과는 측정하지 않았다.** 스킬 도입이 실제로 컨텍스트를 줄였는지, `Edit` 부여가
  비용에 어떤 영향을 줬는지에 대한 수치가 없다. F5의 "비용이 늘었다"는 줄 수 기준 서술이다.

## 6. 판정과 우선순위

**v0.2.2는 공식 기준에서 분명한 개선이다.** 세 축이 모두 공식이 권하는 방향이다 — ① 산문 금지를
`permissions`로 옮김 ② 절차를 상시 로드 문서에서 스킬로 내림 ③ 전량 덮어쓰기(`Write`) 중심에서
수술적 수정(`Edit`) 중심으로 전환. 틀리기 쉬운 사실(백그라운드 도구 필터 목록, trust 함정)을
정확히 인용했고, 근거가 프로젝트 기록에 실재하며, 자기에게 불리한 관측("에이전트가 PM을 반박한
3건, 전부 에이전트가 옳았다")도 남겼다.

남은 결함은 두 종류다.

- **마감 오류** — F1~F4. `settings.json`과 문구 수준의 수정이고, 그중 **F2만 실제 차단 구멍**이다.
- **구조 미완** — F5·G1·G4. 올바른 수단(스킬)을 도입하고도 상시 로드를 줄이지 않았고,
  서브에이전트에 연결하지 않았고, 배포는 여전히 복사다.

제안 순서:

| 순위 | 항목 | 성격 | 범위 |
|---|---|---|---|
| 1 | F2 (`**/` 패턴으로 교체) | 실 구멍 | settings.json 3줄 |
| 2 | F1 (죽은 `Write` 규칙 제거) | 무효 설정 | 사본 settings.json 5줄 |
| 3 | F3 (deny 한계 문구 정정 + sandbox 추가) | 사실 오류 | ORCHESTRATION 1문단, DESIGN_NOTES B1 |
| 4 | F6 (trust 조건 명시) | 숨은 전제 | 설치 스크립트 안내 + ORCHESTRATION 1줄 |
| 5 | F4 (강제 푸시 패턴 보강) | 선택 — 정책 결정 필요 | settings.json, U4 실측 선행 |
| 6 | F5 + G1 (절차 스킬 이전, `skills:` 연결) | 구조 | ORCHESTRATION −45줄, 스킬·에이전트 정의 |
| 7 | G4 (플러그인 배포) | 구조, MINOR 이상 | 별건으로 설계 필요 |

1~4는 시험 전 변경이므로 릴리스 규칙상 `CHANGELOG.md` `[Unreleased]`에 쓰고 태그는 다음 운행
뒤에 붙인다.
