## 0. 긴급 — U1은 오류가 아니다. 양쪽이 **같은 방식으로** 틀렸다

### 사실

공식 sub-agents 페이지의 **Example subagents** 절에 `debugger` 예시가 이렇게 있다.

```markdown
---
name: debugger
description: Debugging specialist for errors, test failures, and unexpected behavior. Use proactively when encountering any issues.
tools: Read, Edit, Bash, Grep, Glob
---
```

본문도 이렇게 적는다.

> A subagent that can both analyze and fix issues. **Unlike the code reviewer, this one includes
> Edit because fixing bugs requires modifying code.**

즉 **`tools` 필드가 있고, `Edit`이 있고, `Write`는 없다.** v0.2.2의 원래 인용("공식 문서의
`debugger` 예시도 `Edit`만 주고 `Write`는 주지 않는다")은 **정확했다.**

### 왜 양쪽 다 "없다"고 결론냈나

페이지 전체가 **110,964자**인데 `WebFetch`는 **앞 100,000자만** 반환하고 뒤 10,964자를 자른다.
`Example subagents` 절은 **잘린 뒤쪽**에 있다. 100,000자 안에는 `--agents` **CLI JSON 예시**에
나오는 다른 `debugger` 항목이 있고, 그쪽에는 `tools`가 없다.

```json
"debugger": { "description": "...", "prompt": "..." }
```

양쪽 세션 모두 그 JSON 예시를 보고 "`tools` 필드가 없다"로 결론냈다. 내가 2라운드에서
**"오류로 확정"** 이라고 쓴 것이 시작이었고, 합의안이 §1 확정 표에 **"양쪽 확인 → U1 오류 확정"**
으로 올려 굳혔다.

### 이게 중요한 이유 — 방법론의 실패

**"두 세션이 독립적으로 확인했다"는 것이 안전장치로 작동하지 못했다.** 같은 도구(`WebFetch`)를
같은 URL에 썼고, 같은 지점(100,000자)에서 잘렸기 때문이다. **독립 검증처럼 보이지만 실제로는
동일한 맹점을 공유한 상관된 검증**이었고, 그 결과 **일치가 오히려 확신을 키웠다.**

이 교차검증 구조의 가치는 1~3라운드에서 충분히 증명됐다(F3은 이 구조가 아니었으면 못 찾았다).
그래서 더더욱 **그 구조가 실패하는 조건을 기록해야 한다.**

- 출처 수신 시 **잘림 여부와 전체 길이를 함께 기록**한다. `WebFetch`는 잘렸을 때 그 사실과
  `offset`을 알려 준다 — 1·2·3라운드 모두 그 경고를 받고도 적지 않았다.
- **"없음"을 결론으로 쓸 때는 전량을 읽었는지 명시**한다. "있음"은 한 군데서 확인되면 참이지만
  **"없음"은 전수를 봐야 참**이다. 이번에 틀린 쪽은 전부 "없음" 결론이었다.
- 두 세션이 같은 도구를 쓰면 **독립이 아니다.** 일치는 신뢰도를 올리지 않는다.

### 조치

- 합의안 **§5의 4번(U1 정정)을 철회**한다. 넣었다면 **맞는 문장을 틀리게 고치는** 결과였다.
- 합의안 §1 확정 표의 해당 행을 **"양쪽이 같은 절단으로 오판 → 4라운드에서 정정"** 으로 바꾼다.
- 대신 **검증 방법론 항목을 신설**해 위 세 줄을 `ORCHESTRATION.md`에 남긴다(§3의 10번).

## 2. fork mode — 인용은 정확했고, **더 맞는 레버가 따로 있다**

### 인용 검증

합의안이 인용한 문장을 페이지 **뒤쪽 10,964자**에서 확인했다. 정확하다.

> Claude Code runs the subagents Claude spawns in the background, forks and non-fork subagents
> alike… **Claude Code also removes the Agent tool's `run_in_background` parameter, so Claude
> can't ask for the foreground.**

§3의 결론 1~4를 수용한다. 특히 **2026-10-08의 "중첩 호출 한계" 진단이 틀렸을 수 있다**는 지적과
**"PM → tester 포그라운드 확인"이 조건부**라는 지적이 맞다.

### 합의안이 놓친 것 — 레버가 두 개이고, 고를 것은 다른 쪽이다

합의안은 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`만 적었다. 같은 절에 **다른 레버**가 있다.

> Set the `CLAUDE_CODE_FORK_SUBAGENT` environment variable to override the defaults:
> * `1` turns fork mode on in non-interactive mode and the Agent SDK as well
> * **`0` turns fork mode off in every kind of session**

둘의 효과가 전혀 다르다.

| 레버 | 효과 | 이 하네스에 미치는 영향 |
|---|---|---|
| `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` | **모든** 서브에이전트를 포그라운드로 | **병렬 실행이 죽는다.** 이번 운행은 FIX3‖FIX4, DOC-A‖B‖C, G3a‖G3b를 병렬로 돌려 시간을 크게 줄였다. 이 레버는 그걸 직렬화한다 |
| `CLAUDE_CODE_FORK_SUBAGENT=0` | fork mode만 끈다 | **백그라운드 기본은 유지**되고, "결과가 있어야 계속할 수 있을 때" 포그라운드로 돈다. `run_in_background` 파라미터도 돌아온다 |

하네스가 원하는 것은 "전부 포그라운드"가 아니라 **"필요할 때 포그라운드를 요청할 수 있는 것"**
이다. 따라서 기록·검토할 레버는 **`CLAUDE_CODE_FORK_SUBAGENT=0`** 쪽이다.
`DISABLE_BACKGROUND_TASKS`는 이 하네스에는 **부적합한 레버**로 적어야 한다.

부수 확인: fork mode가 꺼진 쪽에도 제약이 있다 — "Where fork mode is off and you haven't turned
background tasks off, Claude Code also refuses with an error when a teammate sets
`run_in_background: true`." 팀메이트 경로에만 해당하므로 현재 운영에는 영향이 없다.

## 3. 열린 결정 4건에 대한 답

### Q1. fork mode 레버를 설정에 넣을지 → **넣지 않는다. 문서 기록만.**

1. **미실측**(U8). 이 하네스는 "넣었는데 조용히 안 걸린" 실패를 이미 두 종류 안다(프런트매터 훅의
   trust, `allow`의 trust). `env` 값도 **같은 trust 조건**이다 — 세 번째 같은 실패를 만들 이유가 없다.
2. **해결하려던 문제가 이미 없다.** 레버가 겨냥하는 것은 2026-10-08의 "team-lead가 tester 판정을
   빈 채로 반환"인데, **tester 호출자를 PM으로 옮겨 구조적으로 해소**됐다. 이번 운행에서 PM이
   tester를 2회 직접 호출했고 백그라운드로 받아 문제가 없었다.
3. **비용이 실재한다.** 특히 합의안이 지목한 레버는 병렬을 죽인다(§2).

기록할 내용: fork mode의 존재·기본값·관측 방법(`run_in_background` 파라미터 유무)과 **레버는
`CLAUDE_CODE_FORK_SUBAGENT=0`**이라는 것, 그리고 미실측·trust 조건.

### Q2. 2026-10-08 근거 문장을 어디까지 정정할지 → **3단으로 분리해 적는다. 단정하지 않는다.**

"중첩 호출 한계"를 fork mode로 **교체**하는 것에 반대한다. U9(그 세션의 fork mode 상태는 사후
확인 불가)가 열려 있는데 원인을 바꿔 단정하면, **이번 라운드에서 우리가 방금 저지른 실수(확인되지
않은 것을 확정으로 올리기)를 그대로 반복**한다.

세 줄로 나눠 적는다.

- **관측(2026-10-08)**: team-lead 안에서 `run_in_background: false`를 넣어도 비동기로 전환됐다. — 사실, 유지.
- **당시 진단**: 중첩 호출의 한계로 보았다. — 당시 판단으로 유지하되 "확정 아님" 표기.
- **2026-10-16 재해석**: fork mode가 켜진 세션에서는 그 파라미터가 **제거**되므로 중첩 여부와
  무관하게 같은 결과가 난다. 그 세션이 어느 상태였는지는 사후 확인 불가(U9).

**결정(tester 호출자 = PM)은 유지.** 근거가 하나 흔들려도 다른 근거(공개 관행의 최상위 조율,
이번 운행의 실사용)가 선다.

### Q3. `--force-with-lease`를 허용으로 확정할지 → **`ask` 유지.**

1. **`allow`는 trust 이후에만 적용된다**(F6). `deny`·`ask`는 즉시다. **안전 관련 설정을 조건부로
   만들지 않는다** — 환경에 따라 동작이 갈리는 안전장치는 안전장치가 아니다.
2. 비용이 거의 0이다. 드물게 쓰는 명령이고 프롬프트 1회다.
3. `--force-with-lease`가 안전한 것은 **손실 위험**이지 **의도 위험**이 아니다. PM 행동 규칙이
   요구하는 것은 "외부 반영 전 현재 상태 확인"이고, 프롬프트가 바로 그 지점이다.

### Q4. U3를 "측정하지 않기로 한 것"으로 적을지 → **반대. 측정한다.**

내 2라운드 문장은 **정직성 지적**이었지 "그렇게 확정하자"는 제안이 아니었다. 합의안이 제안으로
읽었으니 정정한다.

측정해야 하는 이유가 하나 더 있다. **이 하네스의 주 경로가 우회 경로다.** 이번 운행에서 `tester`가
네이티브로 노출되지 않아 **13개 에이전트를 전부 `general-purpose` + "정의 파일을 따르라"로** 돌렸다.
즉 `tools:`가 적용되는지 모르는 경로가 **예외가 아니라 기본**이었다.

그리고 이것은 **합의안 §5의 7번(G1)과 직결**된다. `tester.md`에 `skills: baseline-handoff`를
넣어도, tester를 `general-purpose` 우회로 부르면 **그 프런트매터가 적용되는지 알 수 없다.**
U3를 측정하지 않으면 7번은 효과를 모르는 변경이 된다.

측정은 싸다: 정의 파일에 `tools: Read`만 둔 에이전트를 만들고, 우회 경로로 불러 `Write`를
시도하게 한다. 1회면 끝난다.
