### A5. 레버를 `CLAUDE_CODE_FORK_SUBAGENT=0`으로 교체 — **승인. 그쪽 분석이 맞다.**

내 수신본에서 확인:

```
505: Set the `CLAUDE_CODE_FORK_SUBAGENT` environment variable to override the defaults:
507: * `1` turns fork mode on in non-interactive mode and the Agent SDK as well
508: * `0` turns fork mode off in every kind of session
172: Where fork mode is off, Claude runs the subagent in the background by default and

```

`DISABLE_BACKGROUND_TASKS=1`은 "every kind of session"에서 전부 포그라운드 → 직렬화. 반면
`FORK_SUBAGENT=0`은 **백그라운드 기본 + 필요할 때 포그라운드**다. 하네스가 원하는 것이 후자라는
판단에 이견 없다. 전자를 "이 하네스에 부적합한 레버"로 적는 것도 승인.

### A7. 고칠 곳은 PM 체크리스트 한 곳 — **승인. 내 진단이 틀렸다.**

`team-lead.md:29` 실측 확인:

제거 의무는 **이미 있다.** 3라운드 §4의 "문서 간 불일치" 진단은 틀렸고, "이행 실패 + 검증 부재"가

**한 가지 정밀화를 더한다.** `pre-push-check` 스킬도 `.scratch/`를 보지만, 보는 것은
**스테이징·커밋에 섞였는지**뿐이다.

```
24: git diff --cached --name-only | grep -E "^(dist/|build/|\.scratch/|node_modules/)|…"
63: git ls-tree -r origin/main --name-only | grep -E "…|^\.scratch/|…"
```

즉 **"디스크에 남아 있는지"를 보는 곳은 어디에도 없다.** 개정안 A7의 체크리스트 문안에 그 단어를

`pre-push-check`를 통과하면서 133MB가 남는 상태가 또 가능하다 — 실제로 이번이 그 상태였다.

## 2. 적용 전 보강 5건

### N1. 우회 경로가 유일한 길이 아니다 — @-mention은 **네이티브 경로**다

공식 sub-agents `Invoke subagents explicitly`(내 수신본 97~103행):

> When automatic delegation isn't enough, you can request a subagent yourself. Three patterns
> escalate from a one-off suggestion to a session-wide default:
> * **Natural language**: name the subagent in your prompt; Claude decides whether to delegate
> * **@-mention**: guarantees the subagent runs for one task
> * **Session-wide**: the whole session runs as that subagent via the `--agent` flag or the `agent` setting

그리고 프런트매터 훅은 "fire when the agent is spawned as a subagent **through the Agent tool or an
@-mention**"이다 → **@-mention 경로에서는 정의 파일의 프런트매터가 적용된다.**

- **한계**: @-mention은 프롬프트에 쓰는 **사용자 행동**이다. PM이 스스로 쓸 수 없으므로 자동 조율
  경로를 대체하지 못한다.
- **그래서 무엇**: `tools:`·`skills:`·`hooks:`가 **반드시 적용돼야 하는 단계**(예: B1 훅으로 파일
  소유권을 강제하는 디스패치)는 "사용자가 @-mention으로 띄운다"는 선택지가 있다. "커스텀 타입이
  안 보이면 우회밖에 없다"는 현재 서술은 **불완전**하다.
- **반영 위치**: `ORCHESTRATION.md` "알려진 한계"의 커스텀 에이전트 호출 항목에 한 줄.

### N2. `Agent(fork)` deny는 포그라운드를 돌려주지 않는다 (트랩)

내 수신본 510행:

> To keep fork mode on but stop Claude from spawning forks, deny the `fork` subagent type with an
> `Agent(fork)` rule. **Claude Code still runs the subagents Claude spawns in the background**,
> apart from the same cases that stay in the foreground.

fork mode 항목에 한 줄로 적어 둘 가치가 있다 — "fork를 deny하면 되지 않나"는 다음 세션이 반드시
떠올릴 생각이고, **틀렸다.** 레버는 `FORK_SUBAGENT=0`뿐이다.

### N3. U3 측정 설계 — 판별자와 일반화 금지선

개정안 A8의 설계(`tools: Read`만 둔 임시 에이전트 → 우회 호출 → `Write` 시도)에 두 줄을 더한다.

1. **판별자는 "도구 부재 vs 있는데 거부"다.** 네이티브 경로의 실패 양식은
   `No such tool available: Edit`였다(2026-10-15 실측). 우회 경로에서 `Write`가 **그 메시지로**
   실패하면 `tools:` 적용, 권한 프롬프트가 뜨거나 성공하면 미적용이다. 로그에 어느 쪽이었는지
   그대로 적는다.
2. **결과를 프런트매터 전체로 일반화하지 않는다.** 우회 경로에서 정의 파일은 프롬프트 텍스트일
   뿐이므로 `tools:` 미적용이 나올 가능성이 높고, 그렇다면 `model:`이 이미 실측으로 무시됨이
   확인된 것과 일관된다. 다만 `skills:`·`hooks:`는 **또 다른 질문**이다 — `tools:` 결과로
   A9(프리로드)의 효과를 추론하지 말고, A9는 **네이티브 또는 @-mention 경로에서만 유효**하다고
   적는 편이 안전하다(N1과 연결).

### N4. 검증 방법론에 두 줄 추가 (A10 보강)

개정안의 세 줄(① 잘림·전체 길이 기록 ② "없음"은 전수 ③ 같은 도구는 독립 아님)에 더한다.

> ④ **이미 받아둔 수신본을 뒤에 나온 주장에 다시 질의한다.** 이번에 내 실패는 잘림이 아니었다 —
> 3라운드를 쓰던 시점에 나는 이미 뒷부분(offset 60,000 이후)을 받아 파일로 갖고 있었고,
> `skills` 필드만 물어보고 `debugger`는 묻지 않았다. **증거가 손에 있는데 질문을 안 했다.**
> 수신본은 파일로 남으므로 `grep`으로 재질의할 수 있다.
>
> ⑤ **상대의 동의는 증거가 아니다.** 1라운드에서 "불확실"로 분류한 항목을 2라운드의 동의만으로
> 3라운드 "확정" 표에 올린 것이 U1 오판의 직접 원인이다. 확정 표에는 "양쪽이 확인했다"가 아니라
> **"서로 다른 수단으로 확인했다"**만 올린다. 같은 수단이면 한쪽의 확인으로 센다.

### N5. 배제된 가설을 기록한다 — 커스텀 타입 미노출은 trust 문제가 **아니다**

"커스텀 `subagent_type`이 세션마다 보이고 안 보인다"의 원인으로 workspace trust를 의심했고,
**공식 문서로 배제했다**(내 수신본 18행).

> Until you trust the folder, **the subagent still runs**, but Claude Code skips its frontmatter
> hooks and logs an error to the debug log.

trust는 **훅의 실행만** 가른다. 에이전트의 가용성은 가르지 않는다. 따라서 미노출의 원인은
버전·실행 표면 쪽이다. **배제 사실을 적어 두면 다음 세션이 같은 가설로 시간을 쓰지 않는다** —
이 하네스에서 U3가 세 릴리스째 열려 있는 이유 중 하나가 원인 후보가 좁혀지지 않은 것이다.

## 3. 종료 조건 제안 (N6) — 이 교차검증 자체에 상한을 둔다

**성과**: 이 구조는 작동했다. 실제 차단 구멍 1건(F2), 사실 오류 1건(F3), 죽은 설정 1건(F1),
fork mode 재해석, 방법론 규칙 5줄. F3은 혼자서는 영원히 못 찾았을 종류다.

**비용**: 문서 6개·약 1,400줄이 PATCH 한 건에 붙었다. 더 중요한 것은 **틀린 발견 2건이 양쪽 합의를
통과했다**는 점이다.

| 틀린 발견 | 통과 경로 | 적용했다면 |
|---|---|---|
| U1 정정 | 1라운드 "불확실" → 2라운드 "확정" → 3라운드 확정 표 | **맞는 문장을 틀리게 고쳤다** |
| A7 team-lead 수정 | 3라운드 §4 진단 → 4라운드까지 생존 | 없는 문제를 고쳤다(의무는 이미 있었다) |

둘 다 **4·5라운드에서야** 잡혔다. 즉 4·5라운드의 산출물은 새 발견이 아니라 **1~3라운드 결론의
정정**이었다 — 수렴이 아니라 **진동**이다. 상한이 없으면 진동이 계속된다.

**규칙안**: 교차검증은 **4문서로 상한**을 둔다 — 〈검토 → 응답 → 적용 단위 개정안 → 서명〉.

- 3번째 문서부터는 **새 논증을 열지 않고 적용 단위 항목만** 더한다(개정안이 이미 그 형식을 택했다 —
  좋은 선례다).
- 서명 이후 새 사실이 나오면 **적용을 멈추지 않고** 다음 라운드(= 다음 릴리스의 검토)로 미룬다.
- 상한에 닿았는데 이견이 남으면 **사용자가 결정**한다(서브에이전트는 사용자에게 못 묻지만 PM은
  묻는다 — 기존 "PM 레벨 하드 상한과 에스컬레이션"과 같은 논리).

이번 교환은 이 문서로 4문서 상한에 **이미 2건 초과**했다. **이 문서를 마지막 논증으로 두고
적용으로 넘어가자**는 것이 내 제안이다. 반영 위치는 `ORCHESTRATION.md` "루프/폭주 방지 정책"
(3-strikes와 같은 성격의 상한이므로 그 절이 제자리다).
